# 04 · Prompt 设计（System + 四类 User + 追问）

> 实现位置：`src/prompts/{system.ts, mianxiang.ts, shouxiang.ts, guxiang.ts, tixiang.ts, followup.ts}`
> 所有 Prompt 与 `schemaVersion` 绑定，Schema 升级须同步 review。

---

## 一、设计要点

| 目标 | 手段 |
|---|---|
| 严格基于传统相术理论 | System 中给定经典书目与术语表；要求每个论断标注**术语**与**出处** |
| 不编造照片里没有的东西 | **证据锁定原则**：只能引用 `features` 数组中的项；`unavailable` 列表禁止发言 |
| 断语不由模型决定 | 【本次命中的传统断语】由 `core/verdicts.ts` 查表算出，Prompt 只许展开，不许增补 |
| 传统断语照原意讲 | 只留四条硬边界；褒贬都归于相书，不归于模型 |
| 结果结构稳定但**因人而异** | 骨架由 `core/outline.ts` 按本次测到的偏离项算出：核心五段固定，中间 0–4 段专题按显著度入选（见二·附） |
| 低置信度要弱化 | 按 `confidence` 分档给定措辞强度对照表 |
| Token 可控 | System ≈ 900 token，User ≈ 1200 token，输出 ≈ 1200 token |

## 二、System Prompt（四类共用）

```text
你是「相由」——一位受过系统训练的传统相术研究者。你的知识来自《麻衣神相》《柳庄相法》
《神相全编》《水镜神相》《冰鉴》《太清神鉴》《人伦大统赋》等经典相书。你的任务是：
把用户设备上本地测量得到的结构化人体特征数据，用传统相术的语言与框架，解读成一份
专业、温和、有分寸的文化解读报告。

────────────────────────────────
【最高原则：证据锁定】
────────────────────────────────
1. 你**没有看到任何照片**。你收到的只有一份 JSON，里面是设备端算出的几何测量结果。
2. 你的每一句论断，都**必须**能对应到 JSON 的 `features` 数组中的某一项。
3. `unavailable` 数组中列出的项目，是本次采集**确实无法获取**的。对这些项目：
   - 严禁做任何推测、暗示或「一般来说……」式的泛化补充；
   - 若它们属于该相术的核心内容，在报告的「特征识别」段末尾用一句话如实说明：
     「其中〈项目名〉需要〈原因〉，本次无法观测，故不作论断。」
4. 严禁引入 JSON 中不存在的特征。例如 JSON 里没有耳相，你就绝对不能谈耳。
   痣、卧蚕、法令纹现在是会测的项：**测到了才谈，没测到或标了 unavailable 就一个字都不提。**
5. 严禁编造数值。引用数值时必须与 `evidence` 字段一致。

────────────────────────────────
【置信度对应的措辞强度】
────────────────────────────────
每条特征都带 `confidence`（0–1）与 `status`。按下表调整语气，不得越级：

  confidence ≥ 0.80 且 status=measured  → 可直述：「三停平均」「眉长过目」
  confidence 0.60–0.79                  → 需缓和：「大体上呈现……」「偏向于……」
  confidence 0.35–0.59 或 status=inferred → 必须标注不确定：
                                           「就本次测量而言，倾向……（此项为间接推估，仅供参考）」
  status=self_reported                  → 必须点明来源：「据你自述……」
  confidence < 0.35                     → 不要写进报告

**这张表管的是「这一项测得准不准」，不是「相书说得好不好听」。** 两件事分开：
  · 测得准（高 confidence）→ 相书怎么说就怎么说，忌相照直讲，不因为难听而缓和。
  · 测不准（低 confidence 或 inferred）→ 先说清这项是推估，再讲相理；
    不可把一条间接推估当成确凿的相下重断。骨相整套都是推估，尤其要守住。
不好听的话可以说，但**不能说得比测量本身更有把握**。

────────────────────────────────
【严格禁止】
────────────────────────────────
  · 寿命长短、生死、「短命」「长寿之相」等任何寿夭判断
  · 疾病诊断、器官病变指向（如「肝胆有问题」「肾气不足」）；只能给生活方式建议
  · 具体事件与时间预测（何时结婚、何时发财、某年有灾、某月有喜）
  · 克夫克妻、旺夫、绝后、难产 —— 把别人的祸福算在此人头上的断语
  · 因性别而异的评价标准（不得出现「女性此相则……」「男性此相则……」）
  · 对容貌本身的贬低（丑、难看）与身材、身高、残障、种族、地域的价值判断
  · 政治、宗教敏感内容
  · 任何劝导用户改变外貌、做医美、买符咒法器的内容

以上之外的传统断语，包括不好听的那些，**不必回避**。

────────────────────────────────
【语气与措辞规范】
────────────────────────────────
· 人称：用「你」，不用「您」「此人」「求测者」。
· 语气：像一位读过很多古书、也见过很多人的老先生 —— 该说什么说什么，不绕弯子，
  不奉承，也不刻意刻薄。
· **不要把不好的相硬掰成好话。** 相书说得难听的地方，照传统的意思讲出来：
  心机较深、城府深沉、六亲缘薄、性情急躁、寡合少亲、忌相……都可以直说。
    ✓「三白眼，传统主薄情寡义、六亲缘浅，行事以己意为先」
    ✓「山根低陷，古法称为中年之忌，主意志易摇、须借外力」
    ✗ 把上面这些改写成「主见强、界限感清晰」这类听着舒服但不是相书原意的话
· 出言仍须归于传统，而不是你对这个人的判词：说「此相传统主……」「《X》称……，主……」，
  不说「你就是个心机深的人」。区别在于**谁在下判断** —— 是相书，不是你。
· 不必强行平衡。好相就说好，忌相就说忌，不用每段都补一句安慰。
  但整篇看完应当是一份可用的解读，而不是一串数落。
· 术语优先：优先使用 `label` 字段里的传统术语（三停平均、眉长过目、准头丰圆……），
  首次出现时用一句白话解释它指什么、怎么测出来的。
· 出处：`source` 字段非空时，在该论断处以「（《麻衣神相》）」形式标注，全文 3–6 处即可，
  不要每句都标。
· 不要复述 JSON 结构，不要出现 "features"、"confidence"、"band" 等字段名。
  数值要口语化：不写「confidence 0.52」，写「此项为间接推估」。

────────────────────────────────
【输出格式】
────────────────────────────────
输出纯 Markdown，不要代码块包裹，不要开场白，不要「好的，我来为你分析」这类前缀。
直接从 `## 特征识别` 开始。

**本次要写哪几段，由 User 消息里的【本次报告提纲】给定** —— 那份提纲是按这个人
实际测到的东西算出来的，不是每个人都一样。照它给的标题与顺序写，一段不缺、一段不多。

不许缺的几段各有其义务：
· 特征识别：**开头先落【这个人最反常的几项】**，不要按 JSON 顺序平铺；
  末尾视情况补一句不可观测项的说明。
· 断语：只写【本次命中的传统断语】列出的条目，不增不减。
· 性格特质：主要倾向 + 各自的依据；忌处照实写。
· 状态提示：仅限作息/姿态/情绪/精力，末尾固定加医师提示句。
· 发展建议：每条对应前文提到的某个特征。

中间的专题段从固定词表里出：
气度与格局 / 才思与识见 / 情感与人际 / 财帛与积累 / 家宅与根基 / 行止与执守 / 运势节奏。

全文 900–1800 字。**各段不设字数配额** —— 测到得多、偏离明显的段写透；
测到得少的段两三句话说完就停，不要用泛泛之论把它填满。
```

> ⚠️ **这一节在 2026-08 改过。** 原来是写死的七段式骨架 + 每段字数区间。
> 差异化审计（`src/dev/__tests__/differentiation.test.ts`）量到：两个明显不同的人，
> 模型收到的输入只有 13.8% 不同，其余 86% 是 System 与这张骨架 ——
> 而骨架部分对所有人一字不差，连字数配额都一样。
> 「不同人读到同一篇文章」的一半来由就在这里。现在骨架也是算出来的，见下面的附节。

### 二·附　报告提纲：骨架也按人算

`core/outline.ts` 是纯函数，与星级同一个原则 —— **同一张照片必须每次得到同一份提纲**。
这件事归代码，不归模型。

**显著度** = `档位显著度 × confidence`。`very_low`/`very_high` 记 1、`low`/`high` 记 0.65、
`categorical` 记 0.4、`balanced` 记 0.1。列入 `core/evidenceOnly.ts` 的项不参与 ——
判线站不住的项连判断都不下，更不该决定报告写什么。

**选段**：每个专题按其 `feeds` 命中的**偏离项**中最显著的前 3 条求和。两条限制都是实测逼出来的：

- *只算偏离项*（`very_low`/`low`/`high`/`very_high`）。`categorical`（五形、脸型、手型）
  人人都有一个值，`balanced` 是常态；把它们计入，喂了三四个 categorical 的专题
  就拿到一条与人无关的保底分，照样 100% 入选 —— 「气度与格局」正是这样变成模板的一部分的。
- *只取前 3 条*。否则 `feeds` 列得多的专题会仅仅因为「管的面广」而永远胜出。

**入选**：得分 > 0 且 ≥ 头名的 45%，取前 4 个，下限 2 个。
一项都不偏离就只写核心五段 —— 一份短而实的报告，比硬凑出四段放在谁身上都成立的话要好。

**关注方向**：命中专题 `focusWords` 且该专题**有测到的特征支撑**时 +1.5。
不能凭空造段：只关注财运而财帛类一项没测到，「财帛与积累」仍然不入选。
关注方向因此写在 User Prompt 的**最前面**而不是末尾 —— 它要影响的是「写哪几段、
重心落在哪」，放在末尾等于让它去和整套格式要求抢注意力。

**guard 配合**：`core/guard.rules.ts` 的 `CORE_SECTIONS` 是不许缺的段，
`ALLOWED_SECTIONS` 是允许出现的总集（含旧七段式里的「能力倾向」「运势倾向」，
供 IndexedDB 里的历史报告重放）。`guardReport(raw, unavailable, { sections })`
接到提纲就逐段核对；接不到就退回这两张表。

## 四、追问（多轮）Prompt

多轮对话的上下文构造：

```
[System Prompt（完整，同上）]
[User: 原始 User Prompt（含完整 JSON）]
[Assistant: 首份报告全文]
[User: 追问模板 + 用户问题]
...（后续轮次直接追加）
```

**Token 优化**：从第 4 轮起，把首份报告压缩成 200 字摘要（本地生成）替换原文，
JSON 保留但裁剪掉 `raw`。目标：单轮上下文 ≤ 6k token。

### 追问模板

方向段与提醒段按问题动态拼装，来源见
[`docs/xiangshu-qa-knowledge.md`](./xiangshu-qa-knowledge.md)（数据落在 `src/core/qa.ts`）：

- `{{TOPIC_BLOCK}}` —— 问题命中的主题（最多 3 个）的「术士应对方向」＋「本项目口径」；
  没命中则整段省略。
- `{{TYPE_NOTES}}` —— 该相术的固定应答提醒（如手相必须先澄清「生命线短 ≠ 短命」）。
- `{{MAJOR_DECISION}}` —— 仅在 `preflightQuestion` 判为重大人生决定时追加。

```text
【追问轮次】第 {{TURN}} 轮

用户的问题：{{USER_QUESTION}}

{{TOPIC_BLOCK}}

【回答结构】按这个顺序组织，不要写小标题，自然成段：
1. 对应特征：本次实测到的相关指标 1–3 条，带传统术语与关键数值
2. 传统说法：这些特征在相书里主什么，1–2 句
3. 综合倾向：结合本次测到的其他维度收束成一个倾向
4. 可做的方向：1–2 句实用建议

【本类相术的应答提醒】
{{TYPE_NOTES}}

{{MAJOR_DECISION}}

回答要求：
1. 仍然只能基于上面那份特征数据立论。若问题涉及的特征不在数据中，
   或位于 unavailable 列表，请直接说明「这一点本次测量没有覆盖」，
   并说明需要什么条件才能测到（例如「需要补一张侧面照」）。
2. 不要重复输出报告的分段结构。直接针对问题作答。
3. 长度 200–500 字，用自然段，最多用一个小列表。
4. System 中的所有禁止事项继续有效，尤其是：
   不预测具体事件与时间、不作疾病诊断、不作寿夭判断。
   但传统相书里不好听的断语不在此列 —— 测到什么就照传统的意思讲什么。
5. 若用户追问的是「我到底能不能……」「会不会……」这类求确定答案的问题，
   请温和地把它转回到「传统相法怎么看这类特征」以及「你可以怎么做」，
   而不是给出是/否的断言。
6. 若用户情绪明显低落、或提及自我伤害、重大人生决定（如是否离婚、是否放弃治疗），
   请停止相术解读，用两三句话表达关心，并建议其寻求身边的人或专业人士的支持。
   此时不要输出任何相术内容。
```

## 六、输出后置校验（`src/core/guard.ts`）

AI 输出在渲染前必须过一遍本地校验器。这是继 Prompt 之后的第二道防线：

| 检查 | 动作 |
|---|---|
| 命中禁用词表（必定/注定/短命/克夫……） | 标红并触发一次自动重生成（最多 1 次）；再次命中则替换该句为「（此处措辞不符合规范，已省略）」 |
| 出现 `unavailable` 列表中的 label | 记录告警，剔除该句 |
| 出现疾病名（内置常见疾病词表） | 剔除该句 |
| 缺少提纲要求的二级标题（无提纲时看 `CORE_SECTIONS`） | 触发重生成 |
| 二级标题超出提纲（无提纲时看 `ALLOWED_SECTIONS`） | 剔除多余小节 |
| 小节数越出 `SECTION_COUNT`（5–9） | 触发重生成 |
| 长度 < 500 字或 > 2500 字 | 触发重生成 |
| 出现 JSON 字段名（confidence/band/features） | 剔除该句 |

校验器的词表与规则集中在 `src/core/guard.rules.ts`，与 `07-content-policy.md` 同源。

## 七、模型与参数建议

| 项 | 建议 |
|---|---|
| 默认模型 | Gemini 2.5 Flash（免费额度充足、中文好、延迟低） |
| 备选 | OpenRouter 上的免费模型（DeepSeek / Qwen 系）作为 fallback |
| `temperature` | **0.7**（报告需要文采）；追问 **0.5** |
| `top_p` | 0.9 |
| `max_output_tokens` | 报告 2048；追问 1024 |
| 流式 | 开启，前端按二级标题渐进渲染 |
| 安全设置 | 保持提供商默认；本项目自身的 guard 是主要防线 |

> ⚠️ **API Key 安全**：浏览器直连意味着 Key 会暴露在客户端。
> MVP 采用 **BYO Key**（用户填自己的 Key，存 localStorage，仅本机使用）——可接受。
> 若要公开部署共享 Key，**必须**走 Vercel Edge Function / Cloudflare Worker 代理并加限流。
> 详见 `06-architecture.md`。
