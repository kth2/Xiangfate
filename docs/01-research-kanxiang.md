# 01 · 参考项目研究与差距分析

> 第一步「研究与总结」产出之一。
> 研究对象：[timerzz/kanxiang](https://github.com/timerzz/kanxiang)（主要对标）、lincerely/Face-Reading、bz51/AIFace、YeyunLU/Face2Fate。

---

## 一、kanxiang 项目全貌

### 1.1 它是什么

kanxiang **不是一个 App，而是一个 Claude Code Skill**（遵循 AgentSkills 开放标准）。全仓库只有 8 个文件、约 2000 行 Markdown，没有任何可执行代码：

```
kanxiang/
├── SKILL.md            255 行  技能入口（frontmatter + 分析流程定义）
├── README.md           337 行  中文文档（含 3 个完整报告样例）
├── README_EN.md        337 行  英文文档
├── LICENSE                     MIT
└── references/
    ├── mianxiang.md    221 行  面相规则（三停、五官、十二宫、气色、五形、男女相）
    ├── shouxiang.md    235 行  手相规则（手型、掌线、指形、掌丘、色泽、左右手）
    ├── guxiang.md      268 行  骨相规则（九骨、头型、体骨、粗细、骨肉关系、特殊骨相）
    └── tixiang.md      387 行  体相规则（体型、部位、体态、比例、肌肤、声音、气质、衣着）
```

### 1.2 它的工作原理（关键结论）

```
上传照片 → 视觉大模型（analyze_image）直接看图 → 读取对应 references/*.md
       → 大模型自己在脑内把「图像观察」对齐「规则文本」 → 输出 Markdown 报告
```

**没有任何量化计算**。所谓「三停比例协调」「眉长过目」全部由视觉模型主观判断，没有数值、没有阈值、没有置信度。规则文件本质上是**喂给大模型的知识提示词（knowledge prompt）**，不是可执行规则引擎。

> 这是我们和 kanxiang 最本质的架构差异，也是本项目的价值所在。详见第三节。

### 1.3 值得直接继承的东西

| 项目 | 说明 | 我们的处理 |
|---|---|---|
| **四大类划分** | 面相 / 手相 / 骨相 / 体相 | ✅ 完全沿用，作为四个功能模块 |
| **知识来源体系** | 《麻衣神相》《柳庄相法》《神相全编》《水镜神相》《冰鉴》《太清神鉴》《人伦大统赋》 | ✅ 沿用，并在每条规则上标注出处 |
| **报告七段式结构** | 基本信息 → 特征识别 → 性格特质 → 能力倾向 → 运势分析 → 健康提示 → 发展建议 | ✅ 沿用为统一报告骨架（见 `04-prompts.md`） |
| **分析原则** | 客观观察 / 规则依据 / 平衡观点 / 实用导向 | ✅ 写入 System Prompt 硬约束 |
| **禁止事项** | 不绝对化断言、不预测具体事件、不涉政、不宣扬迷信 | ✅ 扩充后写入内容安全策略（见 `07-content-policy.md`） |
| **免责声明文案** | 「本分析基于传统相术理论，仅供文化参考和娱乐……」 | ✅ 作为基础，并加强为多层免责（见 `07`） |
| **术语体系** | 三停、十二宫、九骨、五形、掌丘 | ✅ 作为特征命名的中文标签 |

### 1.4 必须修正的东西

kanxiang 的规则库里有若干条目**不适合直接放进面向公众的 App**，原因是人格贬损、性别刻板印象、寿命/疾病断言，或根本无法从照片获得。完整清单与改写方案见 [`07-content-policy.md`](./07-content-policy.md)，此处仅举例：

| 原文（kanxiang） | 问题 | 处理 |
|---|---|---|
| 耳小薄削：福气浅薄，**短命之相** | 寿命断言 | 删除后半句，改为「传统认为宜注重休养生息」 |
| 三白眼/四白眼：**为人薄情**，六亲缘浅 | 人格贬损 | 改为中性描述「传统称此眼型者主见强、界限感清晰」 |
| 女性忌相：颧骨高耸→**婚姻不顺**；人中浅平→**难产之虞** | 性别刻板 + 医疗断言 | 整节删除，五官规则不再按性别分「贵相/忌相」 |
| 眼神不正：**心术不正，行事诡诈** | 人格贬损 | 删除 |
| 体相 · 乳房（女性） | 不当身体部位评价 | 整节删除，且 Pose 模型本就不输出该部位 |
| 声音 / 言语 / 睡姿 / 衣着色彩偏好 | 照片无法获取 | 移出自动分析，转为**可选自评问卷**（体相模块） |

## 二、辅助参考项目

### 2.1 lincerely/Face-Reading（Python + dlib + SVM）

**最有价值的部分是它的特征分类体系**——把面部拆成 5 个部位，每个部位若干**离散型态**，每个型态挂一段解读文本（繁体中文，`data/analysis.json`）：

| 部位 | 分类标签 |
|---|---|
| 脸型 face | 圓臉、瓜子臉、由字臉、國字臉、甲字臉 |
| 眉 eyebrows | 連心眉、一字眉、新月眉、八字眉、大刀眉 |
| 眼 eyes | 三角眼、丹鳳眼、桃花眼、垂眼、圓眼 |
| 鼻 nose | 朝天鼻、懸膽鼻、截筒鼻、鷹鉤鼻 |
| 口 mouth | 厚嘴唇、小嘴唇、元寶嘴 |

技术路线：dlib 68 点 landmark → 裁剪各部位 ROI → HOG 特征 → 每部位一个 SVM 多分类器 → 查表输出解读。

**对我们的启发**：
- ✅ **「连续测量值 → 离散型态标签」的两段式**正是我们需要的：MediaPipe 给出几何数值，我们用阈值把它映射成「一字眉/新月眉/…」这种传统术语，再交给 AI 解读。这比 kanxiang 让大模型直接看图可靠得多。
- ✅ 直接借用这套**中文型态标签词表**作为我们特征分类的枚举值。
- ❌ 不采用 SVM：需要训练数据、模型文件、且 68 点远少于 MediaPipe 的 478 点。我们用**基于几何比例的规则分类**，可解释、零训练、可调阈值。

### 2.2 bz51/AIFace（Java + 百度人脸 API）

Spring Boot 服务，调用百度 AI 开放平台拿 **105 个关键点**（`data.json` 中可见 `landmark_num: 105` 及 `pose` 三轴角度），前端 4 个页面：首页 → 上传 → 特征点可视化 → 分析结果。

**对我们的启发**：
- ✅ **「特征点可视化」这一步是必要的产品环节**——把检测到的关键点画在照片上给用户看，建立信任感。我们的四个模块都要做（面相画 478 点+三停线；手相画掌线；体相画骨架）。
- ✅ 它返回了 `pose: [yaw, pitch, roll]`，用于判断人脸是否端正。我们用 MediaPipe 的 `facialTransformationMatrixes` 做同样的**姿态质量门控**。
- ❌ 不采用云端 API：违背「特征提取放在浏览器端、不上传原图」的要求。

### 2.3 YeyunLU/Face2Fate

Face-Reading 的衍生/扩展（同样的 `shape_predictor_68_face_landmarks.dat`、同样的 `analysis.json`、同样的 5 个 SVM），额外做了标注工具（`Labeling/`）和 RBF 核 SVM 调优。结论与 2.1 相同，不重复。

## 三、核心差距分析：我们要造的不是 kanxiang

### 3.1 架构对比

| | kanxiang | Xiangfate（本项目） |
|---|---|---|
| 特征来源 | 视觉大模型主观描述 | **端侧 MediaPipe 关键点 + 几何计算 + CV** |
| 原图去向 | **上传给云端视觉模型** | **不离开设备**，只发结构化 JSON |
| 结果可复现 | 否（每次描述都不同） | 是（同一张照片 → 同一份特征 JSON） |
| 有置信度 | 无 | **每条特征带 confidence** |
| 阈值可调 | 无 | 规则表集中管理，可调 |
| 隐私成本 | 高 | 低 |
| Token 成本 | 高（图像 token） | 低（纯文本 JSON，约 1–2k token） |
| 可离线 | 否 | 特征提取可离线，仅解读需联网 |

### 3.2 能力差距表（关键·必读）

这是研究阶段最重要的结论：**kanxiang 靠视觉模型可以「看到」的东西，MediaPipe 关键点未必能测到**。逐项盘点：

| 相术类型 | MediaPipe 可直接量化 | 需额外 CV / 推导 | **无法获得（必须处理）** |
|---|---|---|---|
| **面相** | 三停、五眼、五官几何、脸型、对称性、眉眼间距、人中长度 | 气色（像素采样）、饱满/隆起（z + 明暗梯度）、眉毛浓密（灰度占比）、发际线（需分割模型） | 痣/疤（需额外检测）、动态神态 |
| **手相** | 手型、掌长宽比、五指长短、指长比 | **掌纹（自研 CV 管线）**、掌丘饱满度（明暗+z）、色泽 | 干湿手、软硬手、指甲半月纹（分辨率不足） |
| **骨相** | — （无骨骼模型） | 颧/额/颌骨架（从面部轮廓推导）、肩/盆骨（从 Pose 推导）、骨肉关系（轮廓锐度） | **枕骨、顶骨、耳后骨、龙骨、三台骨**（正面照完全不可见） |
| **体相** | 肩宽比、上下身比、四肢比例、站姿、体态角度 | 体型分类（+ 可选分割模型量腰围）、肤色 | **绝对身高、体重、声音、言语、睡姿、衣着色彩** |

**⚠️ 最大的单点风险：手相的掌纹。**
MediaPipe Hands 只给 21 个关键点，全部是**骨骼关节点**，**完全不包含任何掌纹信息**。而生命线/智慧线/感情线/命运线是手相的绝对核心——没有掌纹的手相分析等于没做手相。

解决方案（详见 [`02-feature-rules.md` 第二章](./02-feature-rules.md)）：用 21 个关键点做**透视归一化**，把手掌摊平投影到标准 512×512 画布，再跑一条自研的**掌纹提取 CV 管线**（CLAHE → Gabor 滤波器组 → 二值化 → Zhang-Suen 细化 → 折线追踪 → 按标准掌坐标系的位置先验分类到四大主线）。低置信度时降级为**用户手动校正**（叠加检测结果，用户点选纠正）。

**⚠️ 次要风险：骨相的「九骨」缺三块。**
枕骨（后脑）、顶骨（头顶）、耳后骨在任何正面照里都不可见，且常被头发遮挡。处理原则：在特征 JSON 中显式标记 `status: "unavailable"`，并在 System Prompt 中**硬性禁止 AI 对 unavailable 特征作任何论断**。宁可少说，不可编造。同时骨相改为**两张照片（正面 + 侧面）**采集，用侧面照补足头部前后径，提升头型判断可靠性。

### 3.3 由此确立的三条设计原则

1. **测得到才说，测不到就标记为不可用** —— 每条特征都有 `status` 和 `confidence`，AI 只能基于 `status: "measured"` 的特征立论。
2. **数值先行，术语其次** —— 先算出可复现的几何数值，再映射到传统术语（「三停比 1.02 : 0.98 : 1.00 → 三停平均」），报告中同时呈现两者。
3. **确定性的归代码，生成式的归 AI** —— 特征提取、分级、评分卡全部在本地代码里算死；AI 只负责把结构化特征「翻译」成有温度的传统相术语言。星级评分**不由 AI 生成**（避免每次不一致），由本地规则算出。

## 四、技术栈验证结果（2026-08-01 实测）

| 项 | 结论 |
|---|---|
| `@mediapipe/tasks-vision` 最新稳定版 | **1.0.1**（2026-07-31 发布） |
| 导出的类 | `FaceLandmarker` / `HandLandmarker` / `PoseLandmarker` / `FaceDetector` ✅ 四大模块所需齐全 |
| `face_landmarker.task` | ✅ 可下载，3.76 MB |

| `pose_landmarker_lite.task` | ✅ 可下载，5.78 MB |
